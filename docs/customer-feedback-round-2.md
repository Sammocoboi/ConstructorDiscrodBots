# Замечания заказчика — итерация 2

Дата фиксации: 22.10.2026

Источник: разбор демо-сборки конструктора Discord-ботов. Замечания касаются панели управления ботом, авторизации, профиля бота, шаблонов и тарифного блока.

Этот документ — рабочий бэклог. Сводная таблица задач добавлена в `team-plan.md` / `docs/team-plan.md`, раздел 14.

> **Распределение нагрузки.** По решению тимлида Шухратжон забирает больше задач: простые UI-формы, шаблоны, контракты, runtime и QA. Данила оставляет за собой сложный UI, дизайн-систему и ревью вёрстки. Артём и Саня подключаются как консультанты и ревьюеры по своим зонам, чтобы не размывать ответственность.

Легенда приоритетов:

- **P0** — блокирует приёмку, чиним в первую очередь.
- **P1** — заказчик явно просил, входит в ближайшую итерацию.
- **P2** — просили, но можно вынести после P0/P1; требует уточнения объёма.

Легенда оценки: **S** — до 0,5 дня, **M** — 1–2 дня, **L** — 3+ дня (на одного человека, без ревью и тестов).

## 2. Задачи по участникам

### 2.1. Данила — frontend

#### CF-01. Подсветка активного раздела панели бота (P0)

**Проблема.** При переходе на «Модули», «Команды», «Сценарии» и другие разделы сверху визуально остаётся выбранным «Обзор».

**Причина.** В `frontend/src/layouts/BotLayout.tsx` (строка ~93) сегмент маршрута берётся как `location.pathname.split('/')[5]`. Для пути `/app/bots/:botId/modules` нужный индекс — `4`, поэтому `activeTab` всегда падает в `overview`.

**Что сделать:**

1. Брать раздел как первый сегмент после `:botId` (`parts[4]`), для `/app/bots/:botId` — `overview`.
2. Для вложенных маршрутов (`modules/:moduleId`, `commands/:commandId`, `flows/:flowId`, `flows/:flowId/versions`) подсвечивать родительский раздел (`modules`, `commands`, `flows`).
3. Добавить unit-тест на функцию вычисления активного раздела (вынести в `shared/lib`).
4. Проверить, что `Tabs` синхронизирован с URL и при прямом открытии ссылки, и после browser back/forward.

**Готово, когда:** активный таб совпадает с открытым разделом на всех 8 вкладках и всех вложенных страницах.

#### CF-07. Кнопка «назад» из модулей (P0)

**Проблема.** Стрелка в шапке бота всегда ведёт на `/app`, поэтому из модулей пользователь попадает ко всем ботам, а не к настраиваемому боту.

**Что сделать:**

1. В `BotLayout` стрелка ведёт на `/app/bots/:botId/overview`, если открыт любой раздел бота; на `/app` — только из обзора.
2. Внутри `ModuleDetailPage` оставить отдельную кнопку «Модули» → `/app/bots/:botId/modules`.
3. Добавить хлебные крошки: `Мои боты / <бот> / Модули / <модуль>`; каждая часть кликабельна.
4. Проверить сценарий: бот → модули → модуль → «назад» → модули → «назад» → обзор бота → «назад» → список ботов.

**Готово, когда:** ни одна кнопка «назад» не уводит из контекста текущего бота раньше времени.

#### CF-02. Ревизия иконок (P1)

**Проблема.** Часть значков не отражает действие или повторяется; заказчик просил заменить «некоторые».

**Что сделать:**

1. Собрать у заказчика точный список кнопок (или приложить скриншоты) — без этого возможна вторая итерация правок.
2. Провести аудит всех кнопок и вкладок, свести к одному набору Tabler Icons, размер 16–18 px, `stroke={1.7}`.
3. Предлагаемая замена вкладок бота:
   - Обзор — `IconLayoutDashboard`;
   - Модули — `IconPuzzle` (сейчас `layout`);
   - Команды — `IconTerminal2`;
   - Сценарии — `IconRoute` / `IconGitBranch` (сейчас `bolt`);
   - Сообщения — `IconMessage2`;
   - Гильдии — `IconBuildingCommunity` / `IconServer2`;
   - Статус — `IconActivityHeartbeat`;
   - Профиль бота — `IconUserCircle` / `IconSettings`.
4. Убрать текстовые эмодзи-иконки, если где-то остались; не смешивать filled/outline в одном ряду.
5. Кнопки действий: «Сохранить как шаблон» — `IconBookmark`, «Пригласить» — `IconBrandDiscord` + `IconUserPlus`, «Удалить» — `IconTrash`, «Назад» — `IconArrowLeft`.
6. Обновить `shared/components/icons.tsx` и `AppIcon`, чтобы не было расхождений между страницами.

**Готово, когда:** есть таблица «было → стало», все иконки из одного набора, активное состояние читается без цвета.

1. Поле `visibility` (`private` / `public`) или `is_public`, миграция, индекс.
2. По умолчанию `private`.
3. Эндпоинт `PATCH /bots/{id}` принимает `is_public`; публичная карточка (`GET /public/bots/{slug}`) отдаёт только безопасные поля.
4. Правила: публичного бота может просмотреть любой авторизованный пользователь; настройки, токен, гильдии и intents — только владелец.
5. Добавить в аудит-лог переключение публичности.
6. UI: блок «Доступ» ниже настроек в `BotProfilePage` (совместно с Данилой): переключатель, ссылка, предупреждение.
7. Для Free-тарифа — disabled с подсказкой про Pro, если решим ограничить фичу тарифом.
8. Согласовать с заказчиком, что именно значит «публичный»: карточка в каталоге, возможность приглашения или шаблон. Без этого не кодить.

**Готово, когда:** приватный бот не виден другим, публичный открывается по ссылке без утечки настроек, переключение в аудите.

#### CF-11. Двухфакторная аутентификация (P2)

1. TOTP (`pyotp`), секрет шифруется, резервные коды — хеши.
2. Эндпоинты: `/auth/2fa/setup`, `/auth/2fa/enable`, `/auth/2fa/disable`, `/auth/2fa/verify`.
3. После Discord OAuth при включённой 2FA — короткоживущий challenge-token, полная сессия только после кода.
4. Защита от replay, лимит попыток, аудит.
5. Восстановление: резервные коды + обращение в поддержку/админу.
6. UI: секция в настройках, экран подключения (QR, секрет, код, резервные коды), экран отключения, шаг входа (совместно с Данилой).
7. Уточнить: 2FA на аккаунт или на бота. В Discord-ботах 2FA — это защита аккаунта владельца, а не отдельного бота.
8. Ревью безопасности — Артём.

**Готово, когда:** 2FA включается/отключается, вход без кода невозможен, резервные коды работают, тесты на replay и лимиты.

#### CF-12. Регресс и приёмка (P0)

1. Playwright-сценарии:
   - переключение всех вкладок бота и подсветка активной;
   - возврат из модуля в модули и в обзор бота;
   - вход только через Discord (email-форма недоступна);
   - загрузка аватара/баннера;
   - список гильдий только с правами администратора;
   - страница шаблона с настройками;
   - отсутствие CTA «Перейти на Pro» у Pro-пользователя;
   - сохранение intents и публичности.
2. Проверить пустые, загрузочные и ошибочные состояния.
3. Прогнать на тестовом Discord-сервере, где у тестировщика есть и нет `MANAGE_GUILD`.
4. Собрать чек-лист приёмки и провести демо с заказчиком.
5. Проверить приёмку после каждой волны, а не только в конце.

#### CF-13. Выравнивание контрактов mock/real API (P0)

1. Свести frontend-тип `Bot` и `BotSerializer`: сейчас фронт ждёт плоские `avatarColor`, `bannerColor`, `activity`, `intents`, а backend отдаёт `profile` (JSON) и snake_case.
2. Выбрать один вариант: adapter/DTO на фронте или приведение сериализатора к контракту OpenAPI. Зафиксировать в `docs/api-contract.md`.
3. Проверить все новые поля (`avatar_url`, `banner_url`, `intents`, `is_public`) в обоих режимах.
4. Убедиться, что каждый метод `httpApi` имеет реальный endpoint в backend; сейчас `GET /me/discord-guilds` отсутствует.
5. Обновить типы из OpenAPI (`npm run api:types`), не дублировать руками.
6. Прогнать smoke с `VITE_USE_MOCKS=false`: вход, список ботов, профиль, модули, шаблоны, тариф.

**Готово, когда:** демо на моках и демо на реальном API показывают одинаковый результат, расхождений в типах нет.

#### CF-14. E2E-стенд с двумя Discord-аккаунтами (P0)

1. Подготовить два тестовых аккаунта: админ сервера и участник без `MANAGE_GUILD`.
2. Зафиксировать тестовый сервер, каналы и роли; доступы — только в защищённом хранилище, не в репозитории.
3. Настроить Playwright-профили/фикстуры для входа под разными аккаунтами (или mock-сессиями, если реальный Discord недоступен в CI).
4. Проверить сценарии CF-05: админ видит сервер, участник без прав — нет; прямой URL чужого бота — 403/404.
5. Добавить матрицу «роль × сценарий» в `docs/testing.md`.
6. Подключить быстрый набор к CI, полный — по расписанию.

**Готово, когда:** регресс по правам воспроизводим, а не проверяется руками «на глаз».

## 3. Технические находки, которые надо учесть

1. **Фронтенд по умолчанию работает на моках.** `frontend/src/shared/api/index.ts`: `VITE_USE_MOCKS !== 'false'`. Замечания заказчика сняты на мок-сборке. Все фиксы нужно делать и в `mockApi`, и в `httpApi` + backend, иначе демо разойдётся с реальным API.
2. **Контракт бота расходится.** Frontend `Bot` — плоские `avatarColor`, `bannerColor`, `activity`, `intents`; backend `BotSerializer` отдаёт `profile` (JSON) и snake_case. Нужен adapter/DTO или приведение сериализатора к контракту OpenAPI. Это задача CF-13.
3. **`GET /me/discord-guilds` отсутствует в backend.** Есть только мок. CF-05 — это не только UI-фильтр.
4. **`Bot.intents` уже есть в модели и сериализаторах**, но не выведен в типе `Bot` на фронте и не редактируется в профиле.
5. **Аватар Discord можно обновить через API, баннер бота — нет.** Баннер в профиле конструктора — внутреннее оформление; не обещать синхронизацию с Discord.
6. **2FA противоречит текущему ТЗ** (раздел P2: «2FA вне MVP»). Заказчик просит — фиксируем как P2 и согласуем объём.
7. **Email-вход есть в ТЗ (FR-1.1).** Отключаем флагом, а не удалением кода, чтобы не потерять требование и не сломать тесты.
8. **Шухратжон — точка перегрузки.** У него 10 задач, включая три P0. Если начнёт буксовать, в первую очередь отдаём Даниле CF-06 (UI) и CF-08, а Саня забирает CF-05. Это зафиксировано как план Б.

## 5. Definition of Done для итерации

- Каждый пункт закрыт в mock-режиме и в режиме реального API.
- Контракты mock/real совпадают, типы сгенерированы из OpenAPI.
- Есть тест или E2E на баг, который исправляли.
- Обновлены `docs/api-contract.md`, OpenAPI и типы фронтенда, если менялся контракт.
- Нет секретов, токенов и персональных данных в логах и репозитории.
- Проверено на тестовом Discord-сервере с правами администратора и без.
- Заказчику отправлены скриншоты/видео «до/после» по каждому замечанию.
- Повторная демонстрация: вход через Discord → создание бота → профиль (аватар, баннер, intents, публичность) → модули → возврат → шаблон → тариф.

## 6. Открытые вопросы к заказчику

1. **Иконки:** пришлите, пожалуйста, список кнопок или скриншоты с пометками — какие именно значки не нравятся и что они должны означать.
2. **Публичность бота:** «публичный» — это карточка в общем каталоге, возможность добавления по ссылке или публичный шаблон? От этого зависит модель доступа.
3. **2FA:** защита аккаунта владельца или отдельная защита настроек бота? В Discord 2FA привязана к аккаунту.
4. **Аватар и баннер:** нужно ли синхронизировать аватар с самим Discord-ботом или достаточно оформления в конструкторе? Баннер бота Discord через API не меняется.
5. **Серверы:** показывать только серверы с правом «Управление сервером» или также серверы, где пользователь владелец, но право не выдано явно? (Владелец всегда проходит.)
6. **Тариф:** у пользователя на Pro кнопка должна вести в Stripe Portal или просто открывать страницу тарифов?
