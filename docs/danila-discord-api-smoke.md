**Дата:** 09.11.2026
**Исполнитель:** Данила (frontend)
**Помогают:** Саня — токены и Discord-приложение; Артём — backend/API; Шухрат — стенд и Runtime
**Приоритет:** P0 перед приёмкой
**Оценка:** 0,5–1 день на первый прогон + отчёт
**Связанные документы:** [`real-discord-launch.md`](real-discord-launch.md) §4–5, [`team-plan.md`](team-plan.md) §2.4

---

## 1. Зачем

Frontend уже переведён на реальный API (`VITE_USE_MOCKS=false`), но сценарий
«вход → бот → сервер» ни разу не прогонялся живым человеком на живом Discord.
Mock-тесты это не ловят: ошибки OAuth, токенов, invite-ссылок и прав видны
только на настоящем аккаунте.

Нужно вручную пройти путь пользователя и зафиксировать, где он ломается.

---

## 2. Что входит в проверку

1. Вход на платформу через Discord OAuth.
2. Создание бота с реальным токеном: проверка токена → сохранение → маска.
3. Приглашение бота на тестовый сервер и появление гильдии в UI.
4. Опционально (если поднят Runtime): запуск бота, статус `online`, ответ на `/ping`.

**Не входит:** исправление backend, настройка production-деплоя, проверка
биллинга и шаблонов. Найденные баги — в issues, а не в этот же PR.

---

## 3. Что подготовить до старта

- [ ] Тестовый Discord-аккаунт (не основной личный).
- [ ] Тестовый сервер, где аккаунт — администратор (нужно право «Управление сервером»).
- [ ] Токен тестового бота: попросить у Сани **или** создать свой тестовый
      application (см. §5.1).
- [ ] Поднятый стенд: PostgreSQL + backend; frontend с `VITE_USE_MOCKS=false`.
- [ ] Доступ к DevTools (Network/Console) и менеджеру паролей.
- [ ] Чистый профиль браузера — чтобы проверить вход «с нуля», без старых cookie.

Локальный запуск:

```powershell
docker compose up -d db backend
cd frontend
npm install
npm run dev
```

Если проверяешь на staging — возьми URL и commit SHA у Шухрата и укажи их в отчёте.

## 4. Сценарий 1. Вход через Discord

**Шаги**

1. Открыть `/login` в чистом профиле браузера.
2. Нажать «Войти через Discord».
3. В окне Discord подтвердить доступ приложению.
4. Дождаться возврата на `/auth/callback/discord?code=...`.
5. Обновить страницу (F5) и перейти в дашборд.

**Ожидаемо**

- [ ] Редирект идёт на `discord.com/oauth2/authorize` с `client_id`,
      `redirect_uri=.../api/v1/auth/discord/callback`, scopes `identify email guilds`.
- [ ] Callback принимает `code`, frontend вызывает `POST /api/v1/auth/discord/exchange`
      и получает `200`.
- [ ] После обмена есть сессия: `GET /api/v1/auth/me` (алиас `/api/v1/me`) → `200`,
      видны имя и аватар из Discord.
- [ ] Дашборд открывается без повторного входа; после F5 сессия сохраняется.
- [ ] `GET /api/v1/me/discord-guilds` возвращает только серверы, где пользователь
      администратор (CF-05), без чужих гильдий.
- [ ] В URL, логах и `localStorage` нет access/refresh-токенов; cookies `httpOnly`.

**Типичные причины провала:** `redirect_uri` не совпадает с Developer Portal,
неверный `code_verifier`/`state`, CORS, цикл 401 → refresh → 401.

## 5. Сценарий 2. Создание бота с реальным токеном

### 5.1. Где взять токен

Вариант А — токен тестового бота у Сани (быстрее, ничего создавать не надо).
Вариант Б — свой тестовый бот:

1. [Discord Developer Portal](https://discord.com/developers/applications) → `New Application`.
2. `Bot` → `Reset Token` → скопировать токен в менеджер паролей.
3. Включить `Server Members Intent` и `Message Content Intent`.
4. Токен никуда не коммитить и не вставлять в чат/issue.

Опциональная проверка токена вне платформы:

```bash
curl -H "Authorization: Bot <ТОКЕН>" https://discord.com/api/v10/users/@me
```

Ожидается JSON с `id`, `username`, `bot: true`.

### 5.2. Проверка в UI

1. Дашборд → «Создать бота».
2. Вставить токен, дождаться проверки, заполнить имя, создать бота.
3. Открыть карточку бота, затем профиль бота. Обновить страницу.

**Ожидаемо**

- [ ] `POST /api/v1/bots/validate-token` → `200`
      `{valid: true, username, applicationId, guildsCount}`; в форме показаны
      имя и аватар бота.
- [ ] `POST /api/v1/bots` → `201`; в ответе `has_token: true`,
      `tokenMasked` вида `••••••••`, `discord_bot_user_id` заполнен.
- [ ] Токен не возвращается в открытом виде ни в одном `GET`/`POST`-ответе
      и не попадает в консоль/логи.
- [ ] После F5 бот на месте, токен по-прежнему замаскирован.
- [ ] Негативный кейс: заведомо неверный токен → `400` с понятным текстом
      на русском, запись бота не создаётся, UI не зависает.

## 6. Сценарий 3. Добавление бота на сервер

1. Открыть бота → «Пригласить» (или `GET /api/v1/bots/{id}/invite-url`).
2. Проверить ссылку, открыть её под тестовым аккаунтом.
3. Выбрать тестовый сервер и подтвердить.
4. Вернуться в платформу, открыть раздел гильдий бота.

**Ожидаемо**

- [ ] `GET /api/v1/bots/{id}/invite-url` → `200` `{url, permissions}`.
- [ ] В ссылке есть `client_id`, `scope=bot applications.commands`, `permissions`;
      при необходимости — `guild_id` и `disable_guild_select=true`.
- [ ] Discord не показывает ошибку «Missing Access»/«Invalid OAuth2 scopes».
- [ ] Бот появился в списке участников тестового сервера.
- [ ] У бота есть базовые права: View Channels, Send Messages, Embed Links,
      Read Message History, Use Application Commands.
- [ ] Гильдия появляется в `/api/v1/bots/{id}/guilds` после синхронизации
      Runtime (или после выбора гильдии в мастере). Если Runtime не поднят —
      отметить пункт как **BLOCKED**, а не как FAIL.
- [ ] Негативный кейс: приглашение на сервер без прав администратора
      блокируется Discord; эта гильдия не появляется в `/me/discord-guilds`.

## 7. Опционально. Запуск бота и `/ping`

Выполнять, только если Шухрат поднял Runtime и бот реально стартует.

- [ ] «Запустить» → статус `starting` → `online` примерно за 15 секунд.
- [ ] В логах Runtime есть подключение к Gateway, heartbeat не просрочен.
- [ ] Slash-команда `/ping` отвечает на тестовом сервере.
- [ ] «Остановить» и «Перезапустить» меняют статус ожидаемо.

Если Runtime недоступен — пропустить и указать в отчёте, что пункт не проверялся.

## 9. Как оформлять дефекты

- Завести GitHub issue с заголовком `[discord-smoke] <что сломано>` и меткой
  `discord-smoke` (если метки нет — попросить Артёма создать).
- В issue: шаги воспроизведения, ожидаемо/фактически, `request_id`, скриншот,
  commit SHA. Токены и cookie — **не прикладывать**.
- Ответственные:
  - OAuth, `/auth/*`, 500 на backend → Артём;
  - токен, `/bots/validate-token`, invite, права, гильдии → Саня;
  - Runtime, статусы, Gateway, стенд → Шухрат;
  - вёрстка, состояния загрузки/ошибки, тексты → Данила.
- Backend-баги не чинить в ветке фронтенда: issue + пинг владельца, чтобы не
  смешивать зоны ответственности.

## 11. Безопасность

- Токен — только в менеджере паролей и в поле формы; после проверки
  тестовый токен отозвать (`Reset Token`) или удалить тестовое приложение.
- Не вставлять токен в issue, чат, скриншоты и логи.
- Не использовать production-токены и личный основной аккаунт.
- Не коммитить `.env`, cookie и дампы БД.
